# Polaris Controller — 設計

この文書は、controller をどう部品に分けるか、各部品が他の部品について何を知ってよいか、
システム全体をどう起動するかを定めます。実装の基準となる文書です。
コードと文書が食い違う場合は、どちらかが誤りです。

[English](design.md) / [日本語](design_ja.md)

## 1. 要件

| # | 要件 | ここでの意味 |
|---|------|--------------|
| R1 | **疎結合** | 部品どうしは 3 節の 4 つの契約だけでやり取りする。他の部品のデータベース・ファイル・設定を読まず、他の部品のロジックを重複して持たない。どの部品も、他を変更せずに差し替え・再起動・停止できる。 |
| R2 | **起動が簡単** | 設定ファイル 1 つとコマンド 1 つで controller 全体が起動する。実行にツールチェーンは要らない。 |
| R3 | **画面は事実を示す** | UI がポリシーについて表示する内容は、backend がルータの実際の状態から計算する。ブラウザ側で組み立て直さない。 |
| R4 | **取り残された状態を作らない** | ホストに影響する controller のデータベース変更には、必ず対応するルータ側の変更が伴う。できない場合は変更を拒否する。 |
| R5 | **壊さずに縮退する** | 障害を起こした情報源は、最後に取得できたデータを一定時間保持する。障害が「ホストなし」「プレフィクスなし」に化けない。 |

対象外: 管理者の認証、controller と agent の間の TLS、controller の高可用性。
代わりに置いている前提は 8 節に書きます。

## 2. 部品

```
                 ┌────────────────────────── controller ホスト ─────────────────────────┐
  ブラウザ ─HTTP─▶│ backend ── UI と REST API (C4) を提供                                │
                 │    │  │                                                             │
                 │    │  ├─HTTP (C2)─▶ neighbor source   (snmp, static, …)              │
                 │    │  └─HTTP (C3)─▶ endpoint source   (ms365, static, …)             │
                 └────┼─────────────────────────────────────────────────────────────────┘
                      └─gRPC (C1)─▶ 各サイト出口ルータ上の agent (go-ra) ─RA─▶ ホスト
```

| 部品 | 責務 | 知っていること | 知らないこと |
|------|------|----------------|--------------|
| **Agent**（go-ra、各ルータ上） | 与えられた設定どおりに RA を送る | 自分のルータの中だけ | ポリシー、グループ、他のルータ |
| **Backend** | ポリシーの保存、コンパイル（Algorithm 1）、全ルータへの反映、UI の提供 | 契約 C1〜C3 | 情報源がデータをどう得るか（SNMP、Microsoft、ファイル） |
| **Neighbor source**（module） | 「サイトのリンク上にどのホストがいるか」に答える | 自分のデータ源と自分のフィルタ | ポリシー、ルータの RA の状態、backend |
| **Endpoint source**（module） | 「サービス X に属するプレフィクスは何か」に答える | 自分のデータ源 | ポリシー、backend |
| **Frontend** | REST API を表示する | 契約 C4 | Algorithm 1、RA 設定、情報源 |

この表から導かれること:

* frontend はポリシーのロジックを**持ちません**。プレビューと差分は
  `GET /api/policy/plan` から取得します。
* インターフェースでの近隣の絞り込みは**情報源の仕事**です（ルータのインターフェース名を
  知っているのは情報源です）。backend はフィルタを渡しません。
* module とは、C2 または C3 を実装した HTTP サーバのことです。追加に必要なのは設定への
  URL の追記だけで、backend の変更は要りません。

## 3. 契約

### C1 — Agent（gRPC、`gora.v1.GoRAService`）

`controller/backend/api/gora/v1/gora.proto` で定義します。backend が使うのは
`ListInterfaces`、`AddInterface`、`UpdateInterface`、`DeleteInterface`（`skip_goodbye`）、
`SendRA`、`GetStatus` です。backend が所有するのは `description` が `polaris-policy` の
設定だけで、それ以外の設定は変更しません。

### C2 — Neighbor source（HTTP）

| メソッドとパス | 応答 |
|----------------|------|
| `GET /api/neighbors` | `200` と JSON 配列（下記）。いま RA を受け取れるホストだけを返す。 |
| `POST /api/neighbors/refresh` | 任意。情報源がデータを更新し終えたら `204`。持たない情報源は `404` か `405`。 |
| `GET /health` | プロセスが動いていれば `200`。 |

```json
[{ "ip": "fe80::1", "lladdr": "02:00:00:00:00:01", "ifindex": 3, "ifname": "eth1",
   "state": "REACHABLE", "is_router": 0, "source": "router-a", "updated_at": "2026-11-20T01:02:03Z" }]
```

`ip` は必須です。backend はリンクローカルのユニキャストアドレスだけを残します。
他の項目は参考情報です。情報源はメモリ上のデータで応答します（backend の待ち時間は最大 5 秒）。

### C3 — Endpoint source（HTTP）

| メソッドとパス | 応答 |
|----------------|------|
| `GET /api/fqdn/services` | `200` と `[{ "name": "Teams", "description": "…" }]` |
| `GET /api/fqdn/services/{name}/endpoints` | `200` と `{ "fqdns": [], "ipv4_prefixes": [], "ipv6_prefixes": ["2603:1027::/48"] }`。知らないサービスは `404` |
| `GET /health` | プロセスが動いていれば `200`。 |

backend が使うのは `ipv6_prefixes` だけです。データの読み込みに失敗しただけの情報源は、
空のリストを `200` で返してはいけません。`503` を返します。

### C4 — Controller REST API

パスはすべて `/api` の下です。エラーは `{"error": "<メッセージ>"}` と 4xx / 5xx の
ステータスで返します。メッセージは管理者が読む前提で書きます。

| メソッドとパス | 用途 |
|----------------|------|
| `GET /health` | 生存確認 |
| `GET /routers`、`POST /routers`、`PUT /routers/{id}` | 一覧、登録、編集 |
| `DELETE /routers/{id}[?force=1]` | 撤去（5.4 節） |
| `GET /routers/status`、`GET /routers/{id}/status`、`GET /routers/{id}/interfaces` | agent が報告する状態 |
| `GET /rules`、`POST /rules`、`PUT /rules/{id}`、`DELETE /rules/{id}` | ルール。削除すると全グループからも外れる |
| `GET /groups`、`POST /groups`、`PUT /groups/{id}`、`PUT /groups/{id}/rules`、`DELETE /groups/{id}` | グループ |
| `GET /neighbors`、`POST /neighbors/refresh` | neighbor source が見つけたホスト |
| `GET /fqdn/services`、`GET /fqdn/services/{name}/endpoints` | endpoint source が知っているサービス |
| `GET /sources` | 各情報源の状態（6 節） |
| `GET /policy/plan` | いまの下書きを適用すると何が起きるか（5.2 節） |
| `POST /policy/apply[?dry_run=1]` | 下書きを適用する（5.3 節） |

検証はここで 1 回だけ行い、正規形で保存します。

| 項目 | 規則 |
|------|------|
| ルータの `name`、`address` | 必須。どちらも重複不可（agent 1 つがルータ 1 台）。アドレスを変更すると、ルール（下書きと適用済みの両方）も新しいアドレスへ移る。 |
| ルータの `policy_source_address` | 空、またはリンクローカルのユニキャストアドレス |
| ルータの `status` | `active` か `inactive` |
| ルールの `nexthop` | 登録済みルータのアドレスか ID |
| ルールのエントリ | `{"type":"ipv6","value":"<prefix>"}` — IPv6 のプレフィクスかアドレス。マスクした形で保存する。または `{"type":"service","value":"<name>"}` — 適用時に解決する（5.5 節） |
| グループの `members` | リンクローカルのユニキャストアドレス。正規形で、重複なし |
| グループの `rules` | 存在するルールの ID |

## 4. データモデル

```
Router  id, name, address, interface, policy_source_address, status, RA パラメータ
Rule    id, comment, nexthop → Router, entries[]            （論文の「D → n」）
Group   id, name, members[], rules[] → Rule                 （「G」と「f(G)」）
AppliedPolicy   最後に成功した適用の時点のルールとグループ、およびその時刻
ServiceCache    サービス名 → 最後に解決できたときの IPv6 プレフィクス
```

ルータの `status`: **inactive** のルータはポリシーに参加しません。
そのルータを指すルールは警告付きで無視され、到達できれば次の適用でポリシーの状態が
取り下げられます。到達できなくても、他のルータの処理は止まりません。
停止中や保守中のルータに対して管理者が使うスイッチです。

## 5. ポリシーのライフサイクル

```
 編集（データベース上の下書き） ──▶ plan ──▶ apply ──▶ 適用済みスナップショット ──▶ 定期再適用
                                                                 ▲                        │
                                                                 └────────────────────────┘
```

### 5.1 下書き

ルールとグループの編集はデータベースだけを変更します。適用するまでルータには届きません。

ルータの登録情報はポリシーではなく基盤です。ルータの変更（状態、アドレス、RA パラメータ）は、
次の適用**または**次の定期再適用の、早い方で反映されます。

### 5.2 Plan — `GET /api/policy/plan`

何も変更せずに、適用したら何が起きるかを計算します。

```json
{
  "pending": true,
  "applied_at": "2026-11-20T01:02:03Z",
  "warnings": ["host fe80::1: 2001:db8::/48 is assigned to both Router(a) and Router(b); …"],
  "routers": [{
    "router": "Router(a)", "address": "fd00::a", "status": "active",
    "reachable": true, "error": "",
    "added": 1, "updated": 0, "deleted": 0, "unchanged": 0, "withdrawn": 0,
    "messages": [{
      "source_address": "fe80::face:a", "preference": "medium", "router_lifetime_seconds": 0,
      "routes": ["2603:1027::/48"], "clients": ["fe80::1", "fe80::2"]
    }]
  }]
}
```

`routers` は登録済みルータごとに 1 件で、項目は適用結果と同じです。`messages` は、
そのルータ向けの Algorithm 1 の制御要求メッセージを、実際に送る形で示したものです。
`pending` は、下書きが適用済みスナップショットと異なるときに true になります。
frontend が自前で作っていた YAML プレビューと差分は、このエンドポイントに置き換えます。

### 5.3 Apply — `POST /api/policy/apply`

1. 下書きをコンパイルする（Algorithm 1）。サービスエントリを解決する（5.5 節）。
2. active な各ルータで動いている設定を読み、差分を計算する。
3. **Make**: 全ルータで設定を追加・更新し、新しい RA を送る。
4. **Break**: 手順 3 が active な全ルータで成功した場合だけ、取り下げ RA を送り、その後で設定を削除する。
   取り下げに失敗したルータの設定は残す。次の適用か定期再適用で、取り下げを計算し直せるようにするため。
5. 全ルータが成功したら、下書きを適用済みスナップショットとして保存する。
   そうでなければスナップショットは変えず、適用が成功するまで、定期再適用が前のポリシーを
   維持し続ける。

応答には、ルータごとの追加・更新・削除・変更なし・取り下げの件数と、警告が入ります。
`dry_run=1` を付けると手順 2 で止まります。

### 5.4 撤去 — `DELETE /api/routers/{id}`

ルータは、そのポリシーの状態がホストから消えてから controller を離れます。

1. そのルータを指すルールが、下書きか適用済みポリシーに残っていれば `409` で拒否する。
   メッセージにルールを示す。（ホストは適用済みポリシーに従っている。まだ使われているルータを
   取り下げると、他のルータが広告する前にホストが経路を失う。）
2. ルータ上の `polaris-policy` の設定を削除し、取り下げ RA を送る。
3. データベースの行を削除する。

ルータに到達できない場合、手順 2 が失敗し、要求は `409` で拒否されます。
`force=1` を付けた場合だけ削除し、応答で「lifetime が切れるまで古いポリシーを広告し続ける
可能性がある」ことを伝えます。

### 5.5 サービスエントリ

タイプ `service` のルールエントリは、endpoint source のサービスを名前で指します。
プレフィクスはコンパイルのたびに引くので、情報源側の変更は次の適用か定期再適用で
ルータに届きます。これは他の変更と同じく、新しい広告 → 古い広告の取り下げの遷移になります。
どの情報源も応答しない場合は、最後に解決できたときのプレフィクス（ServiceCache）を使い、
警告を返します。一度も解決できていない場合、そのエントリは何も寄与せず、警告を返します。
複数の情報源のうち一部だけが応答した場合は、応答しなかった情報源の最後に分かっていた
プレフィクスを残します。不安定な情報源のせいで経路が出たり消えたりしないようにするためです。

以前のバージョンが作った「`service` ラベル付きの `ipv6` エントリ」は、
リテラルのプレフィクスのまま扱います。

### 5.6 定期再適用

`reconcile_interval`（既定 60 秒。0 で無効）ごとに、backend は**適用済みスナップショット**を
もう一度適用します。これにより、

* agent が再起動したルータにポリシーが戻り、
* サービスのプレフィクスの変更に追従し、
* ルータに到達できず飛ばされた Break 段階が完了します。

使うのはスナップショットで、下書きではありません。編集途中の内容がタイマーで適用される
ことはありません。適用は直列化されていて、手動の適用とタイマーが重なることはありません。

## 6. 情報源: 障害時の扱い

backend は neighbor source ごとに、最後に成功した取得の結果を保持します。取得に失敗しても
結果はそのまま残ります。`stale_after`（既定は取得間隔の 5 倍）の間成功しなければ、
その情報源のホストを落とし、`GET /api/sources` に失敗として表示します。

```json
{ "neighbors": [{ "name": "neighbor-collector-snmp", "url": "http://127.0.0.1:8084/api/neighbors",
                  "ok": false, "error": "connection refused", "last_success": "…", "count": 187 }],
  "endpoints": [{ "url": "http://127.0.0.1:8085/api/fqdn/services", "ok": true, "error": "", "last_success": "…" }] }
```

グループのメンバーは保存されたアドレスであり、近隣テーブルへの参照ではありません。
neighbor source が失われてもポリシーは変わらず、選択候補の一覧が空になるだけです。

SNMP の情報源の内部でも、ルータ単位で同じ規則を適用します。ポーリングに失敗したルータは、
決まった回数まで、最後に取得できた近隣を保持します。

## 7. 起動

### 7.1 設定ファイルは 1 つ

運用者が編集するのは `controller/param.yaml` だけです。backend の設定と、module ごとの
有効・無効、ポート、固有の設定を書きます。`server.sh` がこれを読み、有効な module と
backend を起動します。各プロセスには、そのプロセスの設定だけを環境変数で渡します。
`param.yaml` を自分で読むプロセスはないので、module は単体でも起動できます。

### 7.2 コマンドは 1 つ

| 環境 | コマンド | 必要なもの |
|------|----------|------------|
| Docker | `controller/` で `docker compose up -d` | Docker |
| Docker なし | `controller/` で `./server.sh` | Go、Node.js（初回のビルド時だけ）、Python 3 と PyYAML |

どちらも同じ `server.sh` を起動します。Docker では、バイナリとビルド済みの UI が入った
1 つのコンテナの中で動きます。

* UI は backend が配信します（`STATIC_DIR`）。そのため**ポートは 1 つ**（既定 8080）で、
  別の Web サーバや開発用サーバは要りません。
* コンテナはホストのネットワークを使います。backend は IPv6 で agent に、SNMP の情報源は
  ルータに届く必要があり、どちらも Docker の IPv6 対応に依存させないためです。
* データベースと module のキャッシュは 1 つのデータディレクトリに置きます
  （Docker では名前付きボリューム）。
* `server.sh` は、足りないものをビルドし、各プロセスが待ち受けを始めるのを（時間制限付きで）
  待ち、どれか 1 つでもプロセスが終了したら自分も終了します。Docker や systemd が全体を
  再起動できるようにするためです。
* `./server.sh dev` は、frontend の開発用に Vite の開発サーバも起動します。

### 7.3 プロセスとポート

| プロセス | 待ち受け（既定） | 到達できる相手 |
|----------|------------------|----------------|
| backend（API と UI） | `:8080` | 管理者 |
| neighbor-collector-static | `127.0.0.1:8083` | backend のみ |
| neighbor-collector-snmp | `127.0.0.1:8084` | backend のみ |
| endpoint-collector-static | `127.0.0.1:8082` | backend のみ |
| endpoint-collector-ms365 | `127.0.0.1:8085` | backend のみ |

module は、`param.yaml` の `listen_host` で指定しない限り、ループバックアドレスで待ち受けます
（module ごとにコンテナを分けている lab では指定しています）。

## 8. セキュリティ上の前提

| 対象 | 前提または対策 |
|------|----------------|
| REST API と UI | 認証なし。backend のポートには管理ネットワークからだけ到達できるようにする。変更を伴う要求は、別の Web サイトからのもの（`Origin` がこのサーバでも `cors_origins` でもない）か、ボディが `application/json` でないものを拒否する。管理者がたまたま開いたページから適用を実行されないようにするため。 |
| Module | 既定でループバックのみ。SNMP の情報源は、`allow_target_registration` を設定したときだけ、HTTP での対象登録を受け付ける（lab が使用）。 |
| Agent の gRPC | TLS も認証もなし。ルータのポート 50051 には controller からだけ到達できるようにする。到達できる者は、サイトの RA を変更できる。 |
| SNMP のコミュニティ文字列 | `param.yaml` に置く。ログには出さない。 |

これらはプロトタイプの配置上の制約であり、本番で頼ってよい性質ではありません。
脅威については論文のセキュリティの節で議論します。

## 9. この設計で変わること

| 変更前 | 変更後 | 要件 |
|--------|--------|------|
| ルータを削除しても、そのポリシー RA が出続けた | 撤去は先に取り下げる（5.4 節） | R4 |
| Active / Inactive の切り替えに効果がなかった | 意味を定義した（4 節） | R3、R4 |
| ルールを削除しても、グループに ID が残った | 同じトランザクションで外す | R4 |
| プレビューと差分を、ブラウザが旧方式で組み立てていた | `GET /api/policy/plan`（5.2 節） | R1、R3 |
| サービスのプレフィクスを、ルール作成時にルールへ写していた | 適用時に解決し、キャッシュを持つ（5.5 節） | R1、R5 |
| 再起動したルータは、誰かが適用を押すまでポリシーなしだった | 適用済みスナップショットの定期再適用（5.6 節） | R4 |
| SNMP の取得に 1 回失敗すると近隣テーブルが空になった | 情報源ごと・ルータごとに最後の成功結果を保持（6 節） | R5 |
| MS365 の情報源がデータを読み込まなかった | 起動時と定期的に読み込み、保存前に検証する | R5 |
| backend が 1 つのインターフェース名を全情報源に渡していた | 絞り込みは情報源の責務 | R1 |
| 停止中の情報源が「プレフィクスなし」に見えた | エラーとして報告する。`GET /api/sources` | R5 |
| 起動に Go・Node.js・PyYAML が必要で、毎回ビルドし、UI は開発用サーバで動いていた | コンテナ 1 つ、ポート 1 つ、ビルド済み（7 節） | R2 |
| module が全インターフェースで待ち受けていた | 既定でループバック | 8 節 |
